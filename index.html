PySide6: Qt, from Python

  • The same Qt classes, called from Python
  • For each Qt module, Shiboken generates a binding that is compiled into a Python extension module: PySide6.QtCore wraps Qt Core, PySide6.QtWidgets wraps Qt Widgets…

    app = QApplication(sys.argv)
    button = QPushButton("Click me")
    button.clicked.connect(lambda: print("clicked"))
    button.show()
    sys.exit(app.exec())

On desktop these are all shared libraries, loaded when your code imports PySide6.

  • PySide6: the official Qt binding for Python, by The Qt Company
  • The full Qt API, not a subset; Qt docs map almost one to one
  • Snippet: smallest Widgets app, same classes, same signals and slots as in C++
  • Made by Shiboken: reads the Qt headers, generates C++ wrapper code
  • Result: one Python module per Qt module, plus two small runtime libraries, PySide's and Shiboken's
  • All of it C++, linked against Qt and Python
  • On desktop: shared libraries, loaded on import; next, what changes on iOS

Why iOS is different

  • No Python on the device: the interpreter and standard library ship inside the app
  • Qt for iOS is static: everything is linked into the app and registered in advance
  • Everything is built and signed with Xcode, on a Mac
  • Simulator and device are different platforms, so separate wheels
  • Python: like Android, has to ship inside the app; here, python.org's official iOS build
  • Static Qt: the main difficulty, next slide; Android is dynamic, like desktop
  • Xcode: our tool generates the project, Xcode builds, signs, installs; on Android our tool makes the finished package
  • Simulator vs device: both arm64, but Apple treats them as different platforms, so one set of wheels each
  • If asked: iOS wheels are tied to one Python version, desktop and Android ones are not; rarely matters, the app carries its own Python

On iOS, Qt and PySide6 are linked statically

Desktop and Android

Qt and PySide6 are shared libraries.

import loads them when the app runs.

iOS

Qt for iOS is static, so PySide6 is static too.

What to link is decided when the Xcode project is generated.

Decided when the project is generated, not at import time.

  • Desktop and Android: import finds the module file, loads it, which pulls in Qt; Qt finds its plugins on disk
  • iOS: no separate files; what to link is decided when our tool generates the Xcode project
  • Xcode then links it all into the app, nothing loaded later
  • So every module and plugin also has to be registered, later slides
  • Why static: not an Apple rule, iOS can load libraries shipped inside the app, Python does exactly that
  • The official Qt for iOS kit is static; dynamic PySide6 on top of it gave duplicate symbols; a shared Qt for iOS didn't build for me
  • If asked about signing: Xcode signs everything, dynamic parts too, so not the reason
  • So how does main.py become that app? Two steps

Two steps: build the wheels, then deploy the app

1. Build the wheels (rarely)

    $ python tools/cross_compile_ios/main.py \
          --qt-install-path ~/Qt/6.12.0 \
          --arch arm64
  • Needs Qt for iOS and Qt for macOS
  • Optional: wheels come from the Qt Downloads page or qtpip
2. Deploy your app (every time)

    $ pyside6-ios-deploy main.py \
          --wheel-pyside   pyside6-...-ios_arm64.whl \
          --wheel-shiboken shiboken6-...-ios_arm64.whl

    open deployment/ios_arm64/<App>.xcodeproj
  • Generates an Xcode project in seconds
  • The target comes from the wheel's platform tag
  • Same shape as Android: one slow step, one fast step; settings in pysidedeploy.spec
  • Step 1, build the wheels
    • Slow, once per target: device, simulator on Apple silicon, simulator on Intel
    • Needs Qt for iOS, plus Qt for macOS for the build tools
    • Most people skip it: wheels from the Qt Downloads page, or qtpip
  • What's in the wheel
    • PySide6 and Shiboken as static libraries, one per Qt module
    • Plus the Qt for iOS kit it was built against, so no separate Qt install
    • What the tool reads from the kit: the libraries and their link info, plugins, plugin names, the minimum iOS version, the headers for main.mm
    • Tied to one Python version; about 80 to 100 MB
  • Step 2, pyside6-ios-deploy
    • The "project is generated" moment from the last slide, where it decides what to link
    • Compiles nothing, takes seconds
    • Needs a Mac with Xcode; for a device, your Apple team id
    • No simulator flag: the target comes from the wheel's name

What to link

    # QtWidgets.prl: what QtWidgets needs
    -framework QtGui         # other Qt modules
    -framework UIKit         # Apple frameworks
    libQt6BundledHarfbuzz.a  # Qt's bundled libraries

The tool starts from your imports and reads each module's .prl, recursively. Qt's own metadata decides what gets linked.

What to copy

    App.app/
      App_bin                 # Qt + PySide6 + Shiboken (compiled code)
      Frameworks/             # Python.framework
      packages/               # third-party packages
      main.py                 # your code

One executable, plus everything else copied in by Xcode build phases.

  • What to link
    • Qt writes a small link-info file next to every module and plugin, the .prl
    • Four kinds, as on the slide: other Qt modules, Apple frameworks, Qt's bundled libraries, built-in resources like styles
    • Followed for plugins too, so a plugin can pull in a module you never imported
    • Comes from Qt's own data, not a hand-kept list that would go stale
    • Two things not in there, added by hand: a DNS library for networking, Qt's iOS entry point
  • What to copy
    • One executable: Qt, PySide6, Shiboken
    • Python stays a framework, standard library next to it
    • Xcode build steps copy in: Python's standard library, PySide6's Python files, your code and QML
    • No Qt or PySide6 libraries or headers copied into the app
  • One project per target; one project for both simulator and device: not solved

main.mm: what to register

Qt: static plugins

    Q_IMPORT_PLUGIN(QIOSIntegrationPlugin)

Linking libqios.a is not enough. The plugin must be imported by class name.

CPython: built-in modules

    PyImport_AppendInittab("PySide6.QtCore",
                           PyInit_QtCore);

There is no dynamic library to load. Every module must be registered before Py_Initialize.

  • Linking puts the code in, but Qt and Python still need a list of what's there
  • Written into main.mm when the project is generated; runs when the app starts, before Python
  • Qt: on desktop, plugins are files found on disk; here no file, so each plugin imported by class name; without it, "plugin not found", tested
  • Python: on desktop, import finds the module file and loads it; here no file, so we tell Python up front: this module is built in
  • In a CMake app, Qt's CMake writes the plugin imports; here our tool does it, from Qt's link info and CMake files
  • The Python half has no CMake equivalent, Qt doesn't know about Python
  • Likely question: why not CMake? Answer in the Questions notes

main.mm: register, then start Python

1. Register

    Q_IMPORT_PLUGIN(QIOSIntegrationPlugin)
    Q_IMPORT_PLUGIN(QSvgPlugin)

    PyImport_AppendInittab("PySide6.QtCore",
                           PyInit_QtCore);
    PyImport_AppendInittab("PySide6.QtSvg",
                           PyInit_QtSvg);

Everything that is linked gets registered.

2. Start Python

    Py_InitializeFromConfig(&config);
    PyRun_SimpleFile(fp, "main.py");

Qt's entry point calls main(), which runs your main.py.

  • Simplified from the real file generated for Tetrix
  • 1. Register
    • Everything linked gets registered: Tetrix imports three Qt modules, registers five; the iOS and SVG plugins pull in two more
    • Why all of them: one module can load another while starting; a missing one, "could not import module"
    • Plugin class names: not the file name, libqios.a is QIOSIntegrationPlugin; read from Qt's CMake files
    • Plugins: platform, images, SVG icons always; network and SQL ones only when used
    • Permission plugins: PySide6 already imports those itself
    • QML apps: QML plugins too, found the same way; Controls without a chosen style get the iOS style
  • 2. Start Python
    • Qt's own iOS entry point runs first, like in any Qt for iOS app
    • It starts the iOS app, then calls our main()
    • main(): registers, starts Python, runs main.py
    • main.py creates QApplication, calls exec(); from there iOS runs the event loop
    • Python runs on a stack Qt reserves, 512 KB by default; fine for our examples, deep call chains not measured yet
  • A module missing from the kit silently drops out of all this, limits slide

All six, in every app: PySide6 itself imports the six Darwin permission plugins.

  • PySide6 itself always imports the six permission plugins, so they're always in the app
  • A permission plugin without its description text gave errors in Xcode, so all six texts are always there
  • Can't be per app: it's built into PySide6, shared by every app
  • Texts are generic; if your app really uses the camera, say, replace that text
  • The rest is standard app metadata; bundle id defaults to com.example.<name>, change it before release

Third-party Python packages

1. Find them

    # pysidedeploy.spec
    [ios]
    packages = numpy,requests

Listed in the spec, or found by scanning your imports.

2. The tool installs them for iOS

    # run by pyside6-ios-deploy, on every deploy
    pip install --target site-packages \
        --platform ios_..._arm64_iphonesimulator \
        --only-binary :all: \
        --extra-index-url <BeeWare index> ...

iOS wheels from PyPI, or BeeWare's index for compiled packages.

  • So far Qt and PySide6; most apps import more
  • New: the tool installs third-party packages itself, nothing by hand
  • Finding them: listed in pysidedeploy.spec, or found by scanning your imports; final list written back to the spec
  • Installing: pip, on every deploy, iOS wheels only, nothing compiled on your machine
  • Compiled packages: from BeeWare's index when PyPI has no iOS wheel
  • Pinning tip: BeeWare's builds are post-releases, so numpy==2.5.0.* rather than ==2.5.0
  • Copied into the app; compiled parts become frameworks, the way Python on iOS expects
  • Ties back: iOS can load code shipped in the app; PySide6 is static only because Qt is
  • Limit: no iOS wheel, no install

Known limits

  • Official Qt for iOS kit only: static, framework layout. Custom builds are not supported
  • The module set follows the kit. A module missing from it is dropped silently, and fails at import
  • One wheel set per target, tied to one Python version
  • Third-party packages need an iOS wheel, on PyPI or BeeWare's index
  • Custom Qt builds
    • Tool expects the official kit's layout
    • Other layouts possible in principle, not supported on purpose, no need seen yet
    • Shared Qt for iOS: also not, tool expects static
    • Need it? Tell us, no date promised
  • Silent drop
    • The wheel only has the modules that were in its kit
    • A module your app needs but the wheel lacks gets skipped everywhere, no warning
    • App starts, then fails on import with "No module named …"
    • First check: the wheel's module list
    • A proper check when the project is generated: on the roadmap
  • One wheel set per target, tied to one Python version
  • Packages: need an iOS wheel, packages slide
  • Having a project, it grew from the Android approach, and CMake is a fair alternative we should discuss.

  • Thank you! Questions?
  • Why not CMake? It would need Qt for macOS installed too, Qt needs that for any cross-compiled kit; today wheels, Python, Xcode are enough
    • CMake could do the Qt half: plugins, linking, the iOS entry point, QML
    • The Python half stays ours either way
    • And PySide6 would need CMake targets for its per-module libraries
  • Shared Qt for iOS? No, tool expects the static kit
  • My own Qt build? Official kit only, other layouts not planned for now
  • QML? Yes, works
  • Package X? Yes if pure Python, or an iOS wheel on PyPI or BeeWare; list it in the spec, or just import it
  • Other add-on modules? Add them to the kit, rebuild the wheels; Qt PDF works
  • App Store? Not tried, not claiming it
  • PyQt? Separate project, not covered
  • Security, if asked: the tool turns settings and downloads into a project and scripts, so treated as untrusted input
    • Values in the Xcode project escaped, can't break out or add keys
    • Paths in the build scripts quoted
    • Wheels unpacked with a path-checked extractor
    • Python download checked against a fixed checksum, also when cached
    • Not claiming every option is validated
