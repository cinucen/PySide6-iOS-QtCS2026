PySide6 is Qt with a different front door

  • The Qt API, generated from the Qt headers by Shiboken, not a hand-written subset
  • One extension module per Qt module: PySide6.QtCore, QtWidgets, QtQml…
  • Signals, slots and properties are decorators; the QMetaObject is built at runtime, no moc step
  • QML types are registered from Python with @QmlElement

    @QmlElement
    class Counter(QObject):
        countChanged = Signal(int)
        _count = 0

        @Property(int, notify=countChanged)
        def count(self):
            return self._count

        @Slot()
        def increment(self):
            self._count += 1
            self.countChanged.emit(self._count)
  • PySide6: the official Qt binding for Python, maintained by The Qt Company, LGPLv3 or commercial
  • Exposes the Qt API, not a subset: Qt docs map to Python almost one to one
  • Shiboken
    • Generator: reads the Qt headers with libclang, driven by typesystem XML files
    • Emits one wrapper .cpp/.h pair per wrapped Qt class, plus module init code
    • Each Qt module becomes one CPython extension module
  • libpyside6 is what makes a Python class a real QObject
    • Signals, slots, properties, dynamic QMetaObject built from the Python class
    • libpyside6qml does the QML side: type registration, attached properties, list properties
  • Snippet: a QML-registered QObject with a property, a signal and a slot
    • Same shape as the C++ equivalent with Q_PROPERTY / Q_OBJECT / QML_ELEMENT
  • Matters later: everything in the generated bindings is C++, so for iOS it is cross-compiled

What a PySide6 build consists of

  • Bindings: generated at build time, one module per Qt module
  • libpyside6, libpyside6qml: the Qt-specific glue
  • libshiboken6: type registry, converters, object lifetime
  • All of it links against Qt and CPython

  • Three layers between your Python and Qt, and all are ordinary native code
    • Generated bindings: one per Qt module
    • libpyside6 / libpyside6qml: Qt-specific behaviour (signals, QMetaObject, QML registration)
    • libshiboken6: generic runtime for any Shiboken binding (type registry, converters, object ownership, signatures)

  • Everything in the middle links against Qt and CPython
    • On desktop these links are dynamic
    • On iOS they are all resolved at link time of the app, next slides

Desktop and Android load everything at runtime

  • import PySide6.QtWidgets finds a shared library next to the package: QtWidgets.abi3.so
  • It links dynamically against the Qt libraries that ship in the wheel
  • Qt finds its platform and image plugins at runtime; QML finds its plugins through qmldir
  • Android: same model, packaged into an APK by pyside6-android-deploy

iOS cannot do any of that.

  • Baseline everybody should have in mind before iOS
    • Python's import system looks on sys.path, finds a binary, dlopens it
    • That binary pulls in the Qt shared libraries; Qt then loads plugins from disk through QPluginLoader
    • QML plugins are found because qmldir names them and the import path points at them
  • Desktop wheels are on PyPI, one wheel set per platform
    • abi3: one binary works across Python versions (limited API)
  • Android has been supported for a while
    • Different packaging (buildozer and python-for-android), same dynamic model
    • The Android tool produces a finished package; the iOS tool will produce an Xcode project
  • Everything that follows is about what replaces each of these runtime lookups on iOS

What iOS asks of us

  • No system Python: interpreter and standard library ship inside the app
  • An app can only run native code that was signed into it
  • Build, sign and launch all go through Xcode
  • Simulator and device are different targets, so different binaries
  • Qt for iOS is already static. Qt solved that half for C++.
  • No pip on the device, no Python installed
    • Interpreter, standard library, Qt and PySide6 all packaged inside the app bundle
    • Layout set by the Python community's iOS support (PEP 730), and we follow it
    • Python for iOS comes from python.org as an XCframework
  • Apple's rule: an app may only run code that was part of it when it was signed
    • So no dlopen of separate PySide6 .so files the way desktop does
  • Simulator and device differ in platform, not only in CPU
    • An arm64 simulator binary and an arm64 device binary are both arm64, but different platforms (Mach-O LC_BUILD_VERSION)
    • Hence one wheel set per target later
  • Last bullet: you already know this half
    • Qt for iOS ships static libraries, Qt's CMake finalizers import and link static plugins for you
    • Qt for iOS with shared libraries is possible too, but has its own problems, so the tool assumes the official static kit

Static Qt, plus an interpreter: two registries

Qt: static plugins

    Q_IMPORT_PLUGIN(QIOSIntegrationPlugin)

Linking libqios.a is not enough; the plugin must be imported by class name.

CPython: built-in modules

    PyImport_AppendInittab("PySide6.QtCore",
                           PyInit_QtCore);

With no .so to load, every module must be in the table before Py_Initialize.

There is no CMake project here. pyside6-ios-deploy fills both registries from Qt's own metadata and writes them into main.mm.

  • The one idea to take from this talk
    • On a static platform there are two independent registries that must be filled at build time
  • Registry 1: Qt's static plugins
    • Familiar to everyone here: Q_IMPORT_PLUGIN(ClassName) somewhere in the final binary
    • In a CMake app, Qt's finalizers (qt_finalize_target) work out the plugin list and generate the imports
    • Verified on our side: link without the import and the plugin is not found at runtime
  • Registry 2: CPython's built-in module table
    • PyImport_AppendInittab maps a module name to its PyInit_ function
    • After that, import PySide6.QtWidgets resolves to something already inside the binary
    • Must happen before the interpreter starts
  • We do not generate a CMake project; we generate an Xcode project directly, so none of Qt's finalizer machinery runs
    • The tool therefore recomputes the same information from what the kit ships
    • Next slides: where each piece comes from
  • Everything else follows from this: why the tool scans imports, why modules are fixed at build time
  • Likely question: why not qt_add_executable? <your answer>; I come back to it on the discussion slide

Two stages

1. Build the wheels
  • Cross-compile PySide6 against one Qt for iOS kit
  • Slow, done rarely
2. Deploy your app
  • pyside6-ios-deploy
  • Fast, done every time

Same shape as Android

  • If you know the Android deployment, this feels the same
    • Heavy cross-compilation is separate from the everyday tool
    • Orchestrator in tools/cross_compile_ios (Android: tools/cross_compile_android); deploy tool is pyside6-ios-deploy (Android: pyside6-android-deploy)

  • One target = one platform and architecture: arm64 device, arm64 simulator, x86_64 simulator for Intel Macs
  • Wheels: build once per Qt version and target, install once, use across many projects
  • Think of stage 1 as "building a Qt-based SDK" and stage 2 as "using it"

Stage 1: cross-compile the wheels


  $ python tools/cross_compile_ios/main.py \
        --qt-install-path ~/Qt/6.12.0 \
        --arch arm64 --simulator

  dist_ios/pyside6-...-cp315-cp315-ios_arm64_simulator.whl
  dist_ios/shiboken6-...-cp315-cp315-ios_arm64_simulator.whl
  • Needs Qt for iOS and the matching Qt for macOS from the Qt installer
  • One run per target; the wheel tag records the target
  • Not needed by app developers: wheels come from the Qt Downloads page, or qtpip
  • The slow part: compiles Shiboken's generated code and PySide6 against the Qt for iOS kit
  • --qt-install-path is the installer root; the tool picks the kit directories from it
    • ios_device or ios_simulator_<arch> for the target kit
    • macos for the host kit, which supplies the host tools during cross-compilation
    • Standard cross-compilation split: host Qt for tools, target Qt for what gets linked
  • You choose the architecture and simulator or device; x86_64 implies simulator
  • Output is a normal wheel with an iOS platform tag, for example ios_arm64_simulator
    • The Python version is in the tag too (cp315): iOS wheels are tied to the Python they were built for, unlike the abi3 desktop and Android wheels
  • Most app developers never run this: it is for whoever produces the wheels (us) and anyone building from source
    • Everyone else gets the wheels from the Qt Downloads page, or with qtpip, Qt's own pip tool (qtpip download PySide6 with the iOS options)
    • There is a --coin mode for Qt's CI, where the Qt layout is different

The toolchain is Qt's own, plus Python


    include(".../lib/cmake/Qt6/qt.toolchain.cmake")

    set(CMAKE_OSX_SYSROOT iphonesimulator)
    set(CMAKE_OSX_ARCHITECTURES "arm64")
    set(BUILD_SHARED_LIBS OFF CACHE BOOL
        "iOS requires static libs" FORCE)

    set(Python_INCLUDE_DIR
        ".../Python.xcframework/ios-.../include/python3.15")
    set(Python_SOABI
        "cpython-315-iphonesimulator")
  • Rendered from a template; it includes the kit's qt.toolchain.cmake
  • Then the normal build: setup.py bdist_wheel with --cmake-toolchain-file, --qt-host-path, --qt-target-path, --plat-name
  • Python headers come from the matching slice of Python.xcframework
  • Excerpt of tools/cross_compile_ios/templates/toolchain_ios.tmpl.cmake, simplified
    • First thing it does is include Qt's own iOS toolchain from the kit, so we inherit Qt's iOS settings (deployment target, sysroot conventions)
    • The Qt cmake directory is queried from the kit (QT_INSTALL_CMAKEDIR) with a small CMake config test, not assumed to be lib/cmake
  • We add: simulator vs device sysroot, architecture, static-only, and the Python location
  • Python_SOABI is set explicitly to a cpython-315-iphoneos / iphonesimulator value so extension modules are named for the right platform
  • The build is the regular PySide6 build driver
    • setup.py bdist_wheel --standalone, plus --cmake-toolchain-file, --qt-host-path, --qt-target-path, --python-target-path, --plat-name, --no-qt-tools
    • The orchestrator only prepares inputs (xcframework download, toolchain file); compilation is CMake inside build_scripts, same as Android
  • The Python.xcframework is downloaded from python.org and checked against a pinned SHA-256, then cached under ~/.pyside6_ios

What is in the wheel


    PySide6/
      libQtCore.a  libQtGui.a  libQtWidgets.a  ...
      libpyside6.a  libpyside6qml.a
      Qt/                       the Qt for iOS kit
        lib/QtCore.framework/   static archive, Headers, .prl
        lib/libQt6EntryPoint.a
        plugins/   qml/   lib/cmake/
    shiboken6/
      libshiboken6.a  Shiboken.a
  • One static archive per binding module, each exporting PyInit_<Module>
  • The whole kit is inside, with headers and metadata
  • So the wheel and the Qt it was built against can never drift apart
  • Layout of the iOS PySide6 wheel as it is today
    • PySide6/libQt<Module>.a: one archive per binding module; the interesting symbol is PyInit_Qt<Module>
    • libpyside6.a and libpyside6qml.a; libshiboken6.a and Shiboken.a come from the shiboken6 wheel
    • PySide6/Qt: the Qt for iOS kit copied from --qt-install-path, static .framework bundles with Headers and .prl, plugins, qml modules, CMake package files, qt.toolchain.cmake
  • Why embed the kit
    • The deploy tool needs the exact archives, .prl files and plugin metadata the bindings were built against
    • It also needs Qt's headers, because the generated main.mm includes QtCore/QtPlugin
    • Result: no separate Qt install on the app developer's machine
  • Size: a wheel is on the order of 80 to 100 MB, and a 96 MB one unpacks to about 355 MB
  • The set of binding modules follows the kit: modules that are not in the kit are not in the wheel (limits slide)

Stage 2: pyside6-ios-deploy


  $ pyside6-ios-deploy main.py \
        --wheel-pyside   pyside6-...-ios_arm64_simulator.whl \
        --wheel-shiboken shiboken6-...-ios_arm64_simulator.whl

  open deployment/ios_arm64_simulator/pyside_app_demo.xcodeproj
  • App + wheels in, Xcode project out
  • Nothing is compiled; it takes seconds
  • No --simulator flag: the target comes from the wheel's platform tag
  • Settings are kept in pysidedeploy.spec
  • The day-to-day tool: main file and two wheels in, Xcode project out
    • Never compiles anything; rerun it whenever the configuration changes
    • Output goes to deployment/<target tag>: device and simulator projects do not overwrite each other
  • What you need: a Mac with full Xcode (not only Command Line Tools), because the project is built with the iOS SDK and simulator runtimes
    • Device builds need an Apple Developer Team ID (--team-id); the simulator does not
    • Other flags: --name, --bundle-id, --app-version, --xcframework-path
  • The target is never asked for
    • A wheel holds binaries for exactly one target, so the tool reads it from the wheel filename
    • It refuses to continue if the PySide6 and shiboken6 wheels disagree
    • Simulator to device: pass the device wheels, that is all
  • Python.xcframework is downloaded and cached on first run, or you pass your own
  • The result is an Xcode project; signing and installing happen in Xcode

  • Your Python and QML imports decide which Qt modules the app needs
  • The kit inside the wheel decides what that means for linking and registration
  • Three steps follow: what to link, what to register with Qt, what to register with Python
  • Same configuration base as the other deploy tools (pysidedeploy.spec), plus an [ios] section: wheels, xcframework path, bundle id, team id, deployment target, signing style

  • Module detection scans your imports, and QML imports for QtQuick modules; the modules line in the spec can override it
  • Resolve: this is the interesting part, three problems that look similar but are not
    • What needs to be linked: .prl files
    • What needs to be registered with Qt: Q_IMPORT_PLUGIN
    • What needs to be registered with Python: the inittab
  • Output: three generated files, covered after the three steps

Step 1: what to link. Qt's .prl files


    # QtCore.framework/QtCore.prl
    QMAKE_PRL_CONFIG = static lib_bundle
    QMAKE_PRL_LIBS_FOR_CMAKE =
      -lz;
      -framework IOKit;
      -framework CoreFoundation;
      -framework Foundation;
      -lm;
      $$[QT_INSTALL_LIBS]/libQt6BundledPcre2.a;
      -framework MobileCoreServices;
      -framework UIKit
  • Start from the imported modules, follow -framework Qt* into the kit
  • Other -framework: Apple SDK frameworks
  • libQt6Bundled*.a (pcre2, harfbuzz, freetype, libpng, libjpeg) and qrc_*_init.cpp.o resource initializers are linked explicitly
  • Nothing is hand-listed, so it follows the kit it ships with
  • Qt writes a .prl next to every module and plugin; QMAKE_PRL_LIBS_FOR_CMAKE lists what that library needs at link time
    • Other Qt modules, Apple system frameworks, Qt's bundled third-party static libs, resource object files, plain linker flags
  • The tool walks it recursively from the app's modules, so the link closure is derived from Qt's metadata instead of a "link everything" list that would rot
    • The module itself is listed before its dependencies, so the static linker can satisfy undefined references in one pass
  • Details worth knowing
    • The .prl contains placeholders such as $$[QT_INSTALL_LIBS] and $$[QT_INSTALL_PREFIX]; we substitute them from the kit's location and checked this against what qmake -query reports
    • Static libs and resource objects need explicit linking: the qrc_*_init.cpp.o objects are what register Qt's built-in resources (style resources, shaders) at startup
    • The plugins' .prl files are walked too, which is how a plugin can pull in a module the app never imported
    • Not in any .prl: -lresolv for QtNetwork (DNS symbols) and libQt6EntryPoint.a; both added by hand
  • Sample is QtCore's .prl from the wheel, abridged

Step 2: what to register with Qt


    # Qt6QIOSIntegrationPluginTargets-release.cmake
    IMPORTED_LOCATION_RELEASE
      ".../plugins/platforms/libqios.a"

    # Qt6QIOSIntegrationPluginTargets.cmake
    QT_PLUGIN_CLASS_NAME "QIOSIntegrationPlugin"
    

    Q_IMPORT_PLUGIN(QIOSIntegrationPlugin)
  • Always: iOS platform plugin, GIF, ICO, JPEG, SVG, SVG icons
  • By module: QtNetwork adds the SecureTransport TLS backend, QtSql adds SQLite
  • The archive name does not give the class name, so we match the archive path in Qt's CMake target files
  • Same problem Qt's finalizer solves for a CMake app: for every static plugin we link, emit Q_IMPORT_PLUGIN(ClassName)
    • The class name is not derivable from the archive file name: libqios.a is QIOSIntegrationPlugin
    • The only place it lives for us is the CMake target files in lib/cmake: QT_PLUGIN_CLASS_NAME on the plugin's target
    • The tool matches the plugin's archive path against IMPORTED_LOCATION_RELEASE across lib/cmake, then reads the class name from the sibling targets file
  • Checked empirically: leaving the import out reproduces "plugin not found" at runtime, even though the archive is linked
  • Which plugins
    • Always linked: libqios (platform), image formats (gif, ico, jpeg, svg), svg icon engine
    • Gated by module: QtNetwork brings TLS (securetransport) and network information, QtSql brings the SQLite driver
    • Six Darwin permission plugins (camera, microphone, bluetooth, contacts, calendar, location): linked always, but not imported here
      • PySide6's own glue code (qtcore.cpp, qtpositioning.cpp) already does Q_IMPORT_PLUGIN for all six, unconditionally, when PySide6 is built
      • Importing them again would double-register
  • The Qt bundled third-party libraries (harfbuzz, freetype and so on) are ordinary static libs, not plugins: no registration concept applies

  • The QML engine resolves import at runtime; the linker knows nothing about it
  • Start from the QML imports in your app, follow the qml/<Module>/objects- paths in each plugin's .prl
  • No Controls style chosen: add the iOS style, Qt's platform default
  • Your own QML directories are copied into the bundle
  • QML plugins are different from regular modules
    • The QML engine resolves imports at runtime from qmldir, not the linker, so the normal module dependency chain does not apply
    • A QML plugin's dependencies on other QML modules show up in its .prl as resource object paths of the form qml/<Module>/objects-..., so that is what we parse
  • Sample: generated imports for the editingmodel example, a QtQuick Controls app, abridged
    • Twelve QML plugin imports on top of the six always-on Qt plugins
    • Including the Basic style, because the iOS style depends on it
  • If the app uses Controls without selecting a style, Qt's default depends on the platform, so we add the iOS style plugin
  • Class names for QML plugins come from lib/cmake/Qt6Qml/QmlPlugins, same trick as for regular plugins
  • App-local QML directories are copied next to the entry script, which is where engine.addImportPath(Path(__file__).parent) in the Python code looks
  • Both Widgets and QML apps work; QML needs libpyside6qml linked too, which the tool adds when QtQml or QtQuick are in use

Step 3: what to register with Python


  // main.mm for Tetrix (excerpt)
  PyImport_AppendInittab("PySide6.QtCore",     PyInit_QtCore);
  PyImport_AppendInittab("PySide6.QtGui",      PyInit_QtGui);
  PyImport_AppendInittab("PySide6.QtWidgets",  PyInit_QtWidgets);
  PyImport_AppendInittab("PySide6.QtOpenGL",   PyInit_QtOpenGL);
  PyImport_AppendInittab("PySide6.QtSvg",      PyInit_QtSvg);
  PyImport_AppendInittab("shiboken6.Shiboken", PyInit_Shiboken);
  • Tetrix imports QtCore, QtGui, QtWidgets. Where do QtOpenGL and QtSvg come from?
  • From the plugins: the iOS platform plugin links QtOpenGL, the SVG plugin links QtSvg
  • Register everything that is linked, not only what you import
  • This is the real generated main.mm for the Tetrix example
  • Tetrix imports three modules; the closure from step 1 has five
    • libqios.prl lists QtOpenGL, libqsvg.prl lists QtSvg; verified in the .prl files of the wheel
  • Why register all of them
    • A linked binding module can pull in another one while it initializes
    • An unregistered one fails at runtime with "libshiboken: could not import module", even though your own code never imports it
  • Only modules that have a lib<Module>.a get an entry: the closure also contains pure C++ Qt internals (QtQmlModels and similar) that have no PyInit_ symbol
  • A PySide-only module with no Qt library behind it (QtQmlFeatures) is added without reading a .prl
  • shiboken6.Shiboken is always registered
  • This is also why a module missing from the kit is a silent problem: it is dropped from all three lists, the app links and starts, then fails on import (limits slide)

Startup: Qt's entry point first, Python second

  1. _qt_main_wrapper is the binary's entry point (libQt6EntryPoint.a), as in any Qt for iOS app
  2. Qt runs UIApplicationMain, then calls our main() on its reserved stack
  3. main() fills the inittab, then Py_InitializeFromConfig: isolated config, UTF-8 mode, home inside the bundle
  4. PyRun_SimpleFile(main.py): your script creates QApplication and calls exec()
  5. exec() jumps back out to UIApplicationMain; iOS drives the event loop
  • The generated project sets LD_ENTRY_POINT to _qt_main_wrapper and links libQt6EntryPoint.a, which is exactly what Qt's own CMake finalizer does for an iOS app
    • It is not in any module's .prl, so the tool adds it explicitly
  • What Qt does, as I read qtentrypoint_ios.mm in qtbase
    • qt_main_wrapper reserves a stack, then calls UIApplicationMain
    • From applicationDidFinishLaunching, a trampoline runs the user's main() on the reserved stack
    • When main() reaches QApplication::exec(), the event dispatcher longjmps back, so UIApplicationMain can spin the run loop at the level iOS expects
    • Later run-loop callbacks jump back into the user stack to process events
  • Consequence for us: the whole Python interpreter, and the Python frames of your script, live on Qt's reserved stack
    • It works today; Tetrix and the QML examples run this way
    • Qt's default size for that stack is 512 KB (Info.plist key QtRunLoopIntegrationStackSize), capped below 1 MB; we leave it at the default
    • We have not measured Python's stack use under deep call chains: open item
  • Python side of main()
    • PyPreConfig with UTF-8 mode before anything touches locale state
    • PyConfig_InitIsolatedConfig, bytecode writing off, argc/argv passed so QApplication(sys.argv) works
    • sys.path: stdlib, lib-dynload, packages, bundle root

What ends up in the app bundle


    pyside_app_demo.app/
      pyside_app_demo_bin       Qt + PySide6 + libshiboken6
      Frameworks/Python.framework
      python/lib/python3.15/    standard library
      packages/PySide6/         .py and .pyi only
      packages/shiboken6/
      main.py                   + your other .py, QML dirs
      Info.plist
  • No Qt or PySide6 .a, headers or .so files in the bundle
  • Python files are plain files; no .pyc is written
  • Why packages/PySide6 at all? The package __init__ and helpers still need to be importable
  • Three Xcode build phases fill the bundle
    • Process Python libraries: the standard library, using the xcframework's own install script
    • Copy PySide6 packages: rsync of PySide6 and shiboken6 without static libs, headers, pycache
    • Copy Python packages: your entry script and the other local .py files at their relative paths, plus app-local QML directories
  • The C extension modules are built into the binary, but the Python side of PySide6 is still a normal package that has to be on sys.path
  • The executable gets its own name (suffix _bin) so it cannot collide with a directory inside the bundle
  • Python.xcframework is embedded and code-signed on copy; this is the one part that stays a framework
  • The generated project also turns off Xcode's debug dylib split, to keep one self-contained binary

Platform details we ran into

  • Six Darwin permission plugins are always imported, so the Info.plist always carries all six usage descriptions
  • QtNetwork needs -lresolv; it is in no .prl
  • Deployment target is read from the kit's qt.toolchain.cmake; a lower value is refused
  • Wheel archives are thin: one binary per target, no universal binary
  • Python runs in UTF-8 mode, isolated from any environment
  • Permission plugins
    • PySide6's glue always Q_IMPORT_PLUGINs the six Darwin permission plugins, so they are always in the binary
    • A permission plugin present without its NS*UsageDescription key gave errors in Xcode, so the generated Info.plist contains all six: camera, microphone, bluetooth, contacts, calendar, location
    • Hence it cannot be made per-app: the registration is baked into a PySide6 build shared by every app
  • -lresolv provides the _res_9_* DNS symbols for QtNetwork; not a framework, so the .prl parsing does not surface it
  • Deployment target: [ios] deployment_target in the spec, empty by default and then taken from CMAKE_OSX_DEPLOYMENT_TARGET in the kit's toolchain file
    • A value lower than the kit's own minimum is rejected, because the app would claim support for OS versions its own Qt binaries cannot run on
    • The empty value is deliberately never written back, so it keeps meaning "follow Qt" across Qt upgrades
  • Thin archives: PySide6's own .a files are built per target
    • The generated project does not pin SDKROOT or EXCLUDED_ARCHS per target; the wheel decides what links
    • One project for both device and simulator is not solved; we generate one project per target

Python packages on iOS

Pure Python
  • Works if you copy the folder next to your code; data files are not bundled
Packages with compiled code
  • NumPy, Pillow, anything with C inside
  • Same problem PySide6 itself had: static linking
  • Not handled by the tool yet

Today the bundle carries your code, PySide6 and Shiboken, nothing else.

  • Question you will get: can I use my favourite package? Two cases
  • Pure Python: just source files
    • Copy the package folder next to your code: bundled and works
    • Not supported yet: declaring it as a dependency
    • Anything that is not a .py file (data files) is not copied
  • Compiled extensions
    • Need a build for iOS; a desktop wheel will not work
    • Today the tool copies PySide6 and shiboken6 into the bundle and your .py files to the root, nothing else
    • Same consequence of static linking as PySide6 itself: the extension has to be built for iOS, linked in and registered before Python starts
  • This is the same two-registries story, one more time, for code that is not ours

Known limits

  • Official Qt for iOS kit only: static, framework layout. Custom builds are not supported
  • The module set follows the kit. A module missing from it is dropped silently, and fails at import
  • One wheel set per target, tied to one Python version
  • C-extension packages are not supported
  • sys.exit(app.exec()) ends the process with exit(), not by returning from main()
  • Custom Qt builds
    • The generated project assumes the .framework layout of the official kit: lib/<Module>.framework with the .prl inside
    • A non-framework build (-no-framework: lib/libQt6Core.a plus include/) is reachable in principle and not supported; deliberate decision, because we know of no need for it yet
    • Qt for iOS can also be built shared, but the tool assumes static archives
    • If you need it, tell us; I cannot promise a date
  • Silent drop
    • The wheel only has bindings for modules that were in the kit it was built against
    • A module named in the app but not in the wheel is skipped in the link list, the plugin list and the inittab, with no diagnostic
    • The app links and launches, then dies with ModuleNotFoundError on import
    • First thing to check when you see No module named PySide6.QtX: the wheel's module list
    • A real build-time diagnostic is on the roadmap
  • Per-target wheels: no universal binary, and the cp315 tag ties a wheel to a Python version
  • C extensions: covered on the packages slide
  • sys.exit and the event loop
    • Every PySide app ends with sys.exit(app.exec()); PyRun_SimpleFile turns an uncaught SystemExit into a direct C exit()
    • Reproduced in a standalone program: the process ends right there
    • Qt's entry point expects main() to return when exec() ends: it records the exit code, restores the stack limit, and lets iOS terminate normally
    • In normal use iOS suspends apps instead of the app quitting; it matters for an explicit Quit action and for testing
    • Not fixed yet

Where we would like input from Qt

  • Plugin metadata without CMake: class names only live in the CMake target files. Is there a supported way to ask a kit what a module needs?
  • Kit contents: add-ons such as Qt PDF need qt-configure-module. Which should the iOS kit include?
  • Entry point: Python runs on Qt's reserved stack, and exit() skips Qt's return path. What do embedders need to know?
  • Build system: a generated Xcode project, or a CMake project that reuses Qt's finalizers?
  • This is the slide for the discussion; these are the places where the PySide side runs into Qt's build metadata
    • Pick one or two depending on who is in the room
  • 1. Plugin metadata
    • For each static plugin we need the class name for Q_IMPORT_PLUGIN. Today we match archive paths against IMPORTED_LOCATION_RELEASE in lib/cmake and read QT_PLUGIN_CLASS_NAME
    • The same problem for QML plugins and their dependency on other QML modules, which we recover from resource object paths in the .prl
    • Question: is there, or should there be, build-system-neutral metadata for this?
  • 2. Kit contents
    • The module set of a PySide6 wheel is the module set of the kit
    • Qt PDF works when installed with qt-configure-module; which add-ons should be part of the kit that the wheels are built from?
  • 3. Entry point
    • The interpreter lives on the reserved user-main stack (512 KB by default, QtRunLoopIntegrationStackSize); we have not measured deep Python call chains
    • Python's exit() path versus Qt's expectation that main() returns after exec()
  • 4. Build system
    • Today: generate main.mm, Info.plist and project.pbxproj directly, and replicate what qt_finalize_target does
    • Alternative: generate a CMake project and let Qt's finalizers do the plugin work, adding only the Python parts
    • Which one would Qt contributors rather maintain?

Takeaways

  • On iOS Qt and PySide6 are static: two registries, filled at build time
  • The tool does not guess: it reads the kit's own .prl and CMake target files
  • Two stages: build the wheels once, pyside6-ios-deploy every time
  • Three things to remember
    • Static linking means two registries: Q_IMPORT_PLUGIN for Qt, the inittab for Python
    • Both lists are derived from what the Qt kit ships with, so the kit decides what an app can use
    • Build the wheels once, run pyside6-ios-deploy every time
  • Your PySide6 app already runs on iOS: same Python, same Qt, same code as on desktop

Android and iOS side by side

Android
  • Wheel tag: cp310-abi3-android_aarch64
  • Qt and PySide6 as shared libraries
  • Packaged by buildozer and python-for-android
  • Tool output: a finished APK or AAB
iOS
  • Wheel tag: cp315-cp315-ios_arm64
  • Qt and PySide6 as static archives
  • Python from python.org's XCframework
  • Tool output: an Xcode project; Xcode builds and signs

Shared: two stages, the target read from the wheel, settings in pysidedeploy.spec

  • Wheel tags are from the released 6.12.0 wheels: the Android wheel is abi3, the iOS wheel is tied to Python 3.15
  • Android runtime comes through buildozer and recipes for python-for-android that initialise PySide6 and shiboken6; iOS uses the Python.xcframework from python.org directly
  • Android deploy produces the final package (APK in debug mode, AAB in release); iOS deploy ends at the Xcode project, so signing and installing are Xcode's job
  • Same on both: separate heavy cross-compile stage, deploy tool that reads the arch from the wheel name, and the pysidedeploy.spec configuration

Hardening the generator

  • Values written into project.pbxproj are escaped, so config text cannot add keys
  • Paths in the generated build-phase shell scripts are quoted
  • Wheels are extracted with a path-checked extractor
  • The Python XCframework download is checked against a pinned SHA-256
  • Config and download code carry Qt's security review tags
  • The tool turns configuration and archives it did not write into a build project and shell scripts, so it is treated as handling untrusted input
    • pbxproj values: quoted and escaped, so quotes, backslashes, semicolons and newlines cannot break out of a value
    • Shell phases: paths go through shlex.quote
    • Wheel extraction: safe_extractall, shared with the other deploy tools
    • XCframework: sha256 of the python.org archive is pinned in the tool and verified on download and on every cached use
  • The source files carry the Qt-Security header (score and reason): critical for the config and download code, significant for the generators
  • I am not claiming complete input validation of every option; do not oversell this slide
